# 实现一个简易编程语言的编译器

> 这是 `miniLang` 项目的**实现侧**实践指南：讲"这台编译器是怎么一步步造出来的、每个阶段写了什么、遇到哪些坑"。
> 概念级别的讲解见姊妹篇《[从零实现MiniLang](./从零实现MiniLang.md)》；这里更偏动手与工程。
>
> 完整代码在 `fundamentals_of_compiling/miniLang`，构建方式：`cmake -B build -G "MinGW Makefiles" && cmake --build build`（Windows / MinGW）。

---

## 1. 引言：造一门语言的三个理由

造一门小语言，是为了让编译原理从"背概念"变成"看得到的东西"：

- **它能验证**：词法、语法、中间代码、解释执行每一步都有真实输入和真实输出。
- **它逼你懂**：任何一个阶段没搞对，程序就跑不出正确结果（或直接崩）。
- **它连成线**：几十个零散概念被一条主线串起来——从字符到结果。

MiniLang 拆成五个文件，恰好就是编译器的五个阶段：

```
token.h  lexer  parser(含ast)  ir  interpreter  main
   词法单元    词法分析        语法分析/AST  中间代码  解释执行
```

---

## 2. 语言设计：先定文法，再定编译器

动手写代码前先回答："我的语言支持什么？" 这决定了后续所有阶段的工作量。

MiniLang 的选择（刻意从简）：
- **值类型**：`int / float / string / bool`
- **语句**：`let` 声明、赋值、`return`、`print`、`if/else`、`while`、块
- **函数**：`func 名(参数){...}`，支持递归
- **运算符**：算术、比较、逻辑，带优先级

> 设计原则：**语言越小，表达力越弱，但编译器的每个阶段都一目了然。** 学习项目宁可"小而完整"，也不要"大而无当"。

---

## 3. 词法分析器：字符 → 记号

**目标**：把一个字符串变成一串 `Token`。每个 `Token` = 类型 + 原文 + 行列。

实现要点（`lexer.cpp`）：
1. **能读就看**：`peek()` 前看不消费，`advance()` 消费并前进——这是手写扫描器的两个原子操作。
2. **最长匹配**：`=` 后看下一个是否 `=` 得 `==`；`!` 后看下一个得 `!=`（单独的 `!` 是逻辑非）。
3. **关键字 vs 标识符**：先按标识符规则读完整串，再查 `keywordType()` 表。

```cpp
case '=': type = (match('=')) ? EQ : ASSIGN; break;
case '!': type = (match('=')) ? NEQ : NOT;   break;
```

**`Token` 里必须记行列号**——否则后面的语法错误、运行时错误的"第几行"无从谈起。

---

## 4. 语法分析器：记号 → AST

**目标**：把线性记号序列还原成树状结构（AST）。

MiniLang 用**递归下降**（自顶向下）。最关键的是表达式优先级，用"层级化"解决：

```
expr ← or ← and ← equality ← relational ← additive ← multiplicative ← unary ← primary
```

低优先级在上层先拆，高优先级在下层先吃。`a + b * c` 因此天然得到 `a + (b * c)`，并且避免了左递归死循环。

运行 `--ast` 能看到这棵树：
```
func fib(n)
  block
    if
      ...
```

---

## 5. AST：删掉不重要的细节

语法分析树会保留括号、分号、每步推导节点，太啰嗦。MiniLang 用 `Expr`/`Stmt` 两个基类细分为各类节点（`ast.h`），只保留能让后续阶段工作的结构。

---

## 6. 中间代码生成：AST → 三地址码

**目标**：把树翻译成一条条与机器无关的指令，即三地址码（`ir.cpp`）。

经典"语法制导翻译"：遍历 AST，每个表达式完成后返回一个**临时变量**，上层拿它当操作数继续拼指令。`fib` 的递归 `fib(n-1)+fib(n-2)` 会生成：

```
t13 = n - 1
t10 = call fib(t13)
t17 = n - 2
t14 = call fib(t17)
t18 = t10 + t14
return t18
```

控制流用"标签 + 跳转"表达（`if !t8 goto L7`），函数调用用 `call`、返回用 `return`。

### 踩过的坑：迭代期间把"指向指令的指针"缓存下来
早期在 `push()` 里把每条 `Jump` 指令的**指针**存到一个待解析列表，等函数生成完再回填跳转目标。但每条指令 `push_back` 进 `vector<Instr>` 都会**扩容搬移**，之前存的指针全部失效，于是跳转目标全是 `-1`，运行直接越界崩溃。

修正：**不要在 push 期间缓存指向容器元素的指针**。改为函数生成完，一次性遍历函数体，按"标签名 → 下标"就地改写每条跳转指令的 `target`。这是"指针悬挂"最典型的一个工程现场，也直接演示了为什么 `vector` 扩容会让迭代器/指针失效。

---

## 7. 语义分析 + 解释执行：让三地址码跑起来

**目标**：解释器 `run()` 一个循环，不断取栈顶帧的指令、执行。它执行的是**中间代码**，而不是 AST——这正是字节码虚拟机的做法。

三个关键概念落地到 `interpreter.cpp`：

- **值**：`struct Value { 类型标签 + 联合 }`，加法遇字符串是拼接、遇浮点/整数按类型决定。
- **符号表 / 环境**：每个函数一页 `map<string,Value>`。
- **栈帧**：`struct Frame { fn, ip, env, retDst, backIp }`。`call` 压帧、`return` 弹帧把结果写回调用方。递归正是靠"帧叠加"实现的，每帧一个独立作用域。

### 语义检查：声明 ≠ 赋值
`let` 生成 `Decl`（建立变量），赋值生成 `StoreVar`（要求变量已存在）。这样 `x = 5;`（没 `let x`）会报"赋值给未声明的变量"——把"声明"与"赋值"这两个概念在语义上区分开。

## 8. 测试与验证

用一个命令行覆盖整条链路的验证比一个个断点更高效：

```bash
# 三个示例应各自得到预期结果
./build/mini.exe examples/basic.mini --run     # 45 10 4 1 ...
./build/mini.exe examples/fib.mini --run       # 55 610 6765
./build/mini.exe examples/let_if.mini --run    # 7 -1 负数 ...
```

错误路径也应**干净报错**而不是崩溃：
- 漏分号 → `语法错误 [行 N]: 期望 ';'`
- 非法字符 `@` → `词法错误: 行N: @`
- 未声明赋值 / 未定义函数 / 除零 → 运行时错误信息

> 调试忠告：这次最折磨人的一个"段错误"其实源于上面第 6 节的向量指针失效——**表现为随优化级别改变、连无关的报错路径都一起崩**。遇到"神秘崩溃"先怀疑内存失效（越界、悬挂引用），而不是无限调条件。用 `-g` + Debug 断言编译能立刻暴露这类问题。

## 9. 总结与扩展

MiniLang 是一个可运行的"前端 + 中端 + 解释执行"骨架。继续长大方向：

- 静态类型标注 + 符号表类型检查
- 块级作用域（每层 `{}` 一个子环境）
- 更多中端优化（公共子表达式、死代码消除）
- 后端：生成汇编、寄存器分配（图着色）——这是"编译器"真正叫"编译"而不仅是"解释"的部分。
