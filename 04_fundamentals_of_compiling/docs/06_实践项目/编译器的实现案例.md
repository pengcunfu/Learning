# 编译器的实现案例：MiniLang 复盘

> 本文件是 `miniLang` 项目的**复盘**：从这个真实的实现里能提炼出什么设计与取舍、遇到了哪些挑战与趋势、以及在它身上做了哪些优化。
> 概念讲解见《[从零实现MiniLang](./从零实现MiniLang.md)》，构建细节见《[实现一个简易编程语言的编译器](./实现一个简易编程语言的编译器.md)》。

## 一、实现案例：MiniLang 选型与取舍

### 1. 为什么是"编译前端 + 中端 + 解释执行"，而不是完整编译？

编译器可以走到不同深度：

| 形态 | 做了哪些阶段 | 适合作什么 |
|------|--------------|-----------|
| **纯解释器** | 词法→语法→直接求值 | 最简，但看不到"中间代码"概念 |
| **编译前端+中端+解释执行**（MiniLang 所选）| 词法→语法→AST→**三地址码**→执行 | 完整覆盖前端与中端，让"中间代码"这一层真实可见 |
| **完整编译器** | 再往后端：生成汇编/机器码 | 工业级，工作量大 |

MiniLang 选中间形态，是为了**把"三地址中间代码"这个常被跳过的中端概念真正跑起来**。解释器直接执行中间代码，本质和现代 Java/JVM、Python/字节码的做法一致——一鱼两吃。

### 2. 实现语言选 C++ 的理由

- 与仓库内理论文档的代码风格一致（用 C++ 解析 HTML/CSS/JS 的主题）。
- 指针、内存、`std::vector` 的"扩容失效"等问题，恰好能借此体会真实编译器的内存管理复杂度。
- 直接用结构体/继承表达 AST、用 `std::vector` 表达指令序列，贴近工业实现。

代价是 C++ 的内存坑（如本文一开头的向量迭代器失效）会比 Python 更"疼"，但这种疼本身就是学习。

### 3. 关键工程决策清单

| 决策 | 选择 | 为什么 |
|------|------|--------|
| 词法分析 | 手写扫描器 | 比 Flex 自动生成更能讲清"状态机手写是怎么回事" |
| 语法分析 | 递归下降 | 自顶向下最直观，一个非终结符一个函数 |
| 表达式优先级 | 层级化函数嵌套 | 天然处理 `a+b*c`，免于手工消除左递归 |
| 中间表示 | 三地址码 | 最经典、最适合教学的中间代码 |
| 解释执行 | 执行 IR，栈帧模拟调用 | 展示运行时作用域，贴近字节码 VM |
| 值表示 | 标签联合（动态类型） | 简单，先跑起来；静态类型留作扩展 |

## 二、编译器设计的挑战与趋势（用 MiniLang 印证）

### 1. 实际遇到的挑战
- **指针/迭代器失效**：`vector` 扩容导致跳转目标回填失败——这是本项目最"真实"的一道坎。
- **声明与赋值的语义区分**：要决定"对未声明变量赋值"是报错还是静默建变量，这属于语义设计决策。
- **类型语义**：`+` 对数值是求和、对字符串是拼接——决定"运行时常量如何按类型分派"。

### 2. 与真实编译器趋势的呼应
- **中间表示的价值**：正因为有了三地址码这一中立层，才能"任何前端 → IR → 任何后端"。LLVM 正是把这个思想推向极致的代表（一套 IR、多种前端与后端）。MiniLang 让你亲手摸到了这层。
- **解释执行 IR ≈ 字节码 VM**：JVM 跑字节码、Python 跑 .pyc，MiniLang 跑自己的三地址码——思想同源。
- **优化发生在 IR 层**：下面第三部分会在三地址码上演示最基础的优化，正是 LLVM pass 的"缩略版"。

## 三、编译器优化实践（在三地址码上做的第一类优化）

### 1. 为什么要优化
中端优化的原则是"**在不改变程序语义的前提下，让代码执行得更快/更小**"。它发生在中间代码层，与源语言和目标机都无关。

### 2. 常量折叠（constant folding）：MiniLang 已内置
最基础也最直观的优化：**编译期把字面运算算掉，不生成指令**。

`print(7 % 3)` 若不做优化会生成 3 条指令：
```
t16 = 7
t17 = 3
t18 = t16 % t17
print t18
```
MiniLang 的中间代码生成器发现 `7 % 3` 两侧都是整数字面量，直接在生成期算成 `1`，只剩一条 `print t18`。这一小步就是"**编译器比运行时更早知道答案**"的朴素体现，也是常量传播/死代码消除的祖先。

对应代码（`ir.cpp` 的 `genExpr(Binary)`）：
```cpp
if (l.type == Operand::T::I && r.type == Operand::T::I && intFoldOk(b.op)) {
    return litInt(foldInt(b.op, l.ival, r.ival));   // 编译期就算掉，不生成指令
}
```

### 3. 更多优化方向（把工作交给"你好编译器"会做什么）
- **公共子表达式消除（CSE）**：`a*b` 出现两次，只算一次存临时变量。
- **死代码消除（DCE）**：没被使用的结果（MiniLang 的 `ExprStmt` 丢弃结果）可以直接不生成。
- **循环不变式外提 / 强度削弱**：把每次循环重复计算但不随循环变化的量移出去。
- 这些优化共同点：**都在三地址码上做等价变换**，不需要回到语法树。

### 4. 如何检验优化效果
用 `--ir` 对比"优化前后"的指令条数。MiniLang 目前只有常量折叠；把它关掉（把 `intFoldOk` 恒判 `false`）就能看到 `print(7 % 3)` 退化为 3 条指令——一对比，优化的作用一目了然。

## 总结

MiniLang 虽小，却踩过了真实编译器里最具代表性的坑（内存失效、语义取舍、中间表示的意义），并亲手实现了第一类优化。把这条"字符 → 记号 → AST → 三地址 → 执行"的线走通后，再看任何工业编译器，你看到的就不再是玄学，而是一连串你已经认识老朋友。
