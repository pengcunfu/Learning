# 符号表（Symbol Table）

## 一、符号表的基本概念

### 1.1 定义与作用

**符号表**是一种存储键值对（Key-Value Pair）的抽象数据类型，支持高效的**查找**、**插入**和**删除**操作。

**核心操作：**
```
put(Key, Value)：将键值对存入符号表
get(Key)：根据键查找对应的值
delete(Key)：删除指定的键值对
```

**扩展操作（有序符号表）：**
```
min()：获取最小键
max()：获取最大键
floor(Key)：获取小于等于Key的最大键
ceiling(Key)：获取大于等于Key的最小键
rank(Key)：获取Key的排名
select(k)：获取排名为k的键
```

### 1.2 符号表的分类

#### 1.2.1 无序符号表
**特点：**
- 键之间没有顺序关系
- 只支持基本操作（put、get、delete）
- 实现相对简单

#### 1.2.2 有序符号表
**特点：**
- 键保持有序（通常升序）
- 支持范围查询和排序相关操作
- 实现相对复杂

### 1.3 应用场景

**典型应用：**
1. **编译器**：变量和函数的作用域管理
2. **数据库**：索引和数据字典
3. **网络**：DNS解析、路由表
4. **文件系统**：文件元数据管理
5. **文本处理**：单词统计、索引构建

## 二、初级实现方式

### 2.1 链表实现

#### 2.1.1 设计思路

**数据组织：**
```
[Key1:Value1] → [Key2:Value2] → [Key3:Value3] → ...
```

**基本思想：**
- 使用链表存储键值对
- 新元素插入到链表头部
- 查找时顺序遍历链表

#### 2.1.2 操作分析

**查找操作：**
- **思路**：从链表头开始，逐个比较键
- **过程**：比较Key → 匹配则返回Value，否则继续
- **复杂度**：O(n) - 需要遍历整个链表

**插入操作：**
- **思路**：先查找，存在则更新，不存在则头插
- **过程**：遍历查找 → 未找到则创建新节点并插入头部
- **复杂度**：O(n) - 查找需要O(n)，插入O(1)

**删除操作：**
- **思路**：查找目标节点，调整指针
- **过程**：遍历查找 → 找到后删除节点
- **复杂度**：O(n) - 查找主导

#### 2.1.3 优缺点分析

**优点：**
- 实现简单
- 插入操作快（找到位置后）
- 内存利用率高

**缺点：**
- 查找效率低
- 不支持有序操作
- 缓存性能差

### 2.2 有序数组实现

#### 2.2.1 设计思路

**数据组织：**
```
数组保持有序：[Key1, Key2, Key3, ...]
值数组：    [Val1, Val2, Val3, ...]
```

**基本思想：**
- 键数组保持有序
- 使用二分查找加速查找

#### 2.2.2 核心操作：rank()

**rank()函数的重要性：**
```
rank(Key)：返回Key在有序数组中的位置

作用：
1. 如果Key存在，返回其位置
2. 如果Key不存在，返回应该插入的位置
```

**二分查找思路：**
```
维护查找区间 [low, high]
每次取中间位置 mid = (low + high) / 2
比较Key与Keys[mid]
- 相等：找到
- 小于：在左半区继续 [low, mid-1]
- 大于：在右半区继续 [mid+1, high]
```

#### 2.2.3 操作分析

**查找操作：**
- **思路**：使用rank()函数定位
- **复杂度**：O(log n) - 二分查找

**插入操作：**
- **思路**：rank()找到位置 → 移动元素 → 插入
- **复杂度**：O(n) - 移动元素是瓶颈

**删除操作：**
- **思路**：rank()找到位置 → 移动元素填补
- **复杂度**：O(n) - 移动元素主导

#### 2.2.4 优缺点分析

**优点：**
- 查找效率高（O(log n)）
- 支持有序操作
- 空间紧凑

**缺点：**
- 插入删除效率低
- 需要移动大量元素
- 大小固定或需要昂贵的resize

## 三、二叉搜索树实现

### 3.1 设计思路

**数据组织：**
```
       [50:V5]
        /    \
  [25:V2]  [75:V7]
   /  \      /
[15]  [30] [60]
```

**核心思想：**
- 利用BST的有序性
- 左子树 < 根 < 右子树
- 递归定义，递归操作

### 3.2 操作分析

**查找操作：**
```
思路：
1. 从根开始比较
2. Key小 → 向左
3. Key大 → 向右
4. 相等 → 找到

复杂度：O(h)，h为树高
平均情况：O(log n)
最坏情况：O(n)
```

**插入操作：**
```
思路：
1. 执行查找操作
2. 找到插入位置（空节点）
3. 创建新节点

复杂度：O(h)
关键：插入位置唯一确定
```

**删除操作：**
```
思路：
1. 查找目标节点
2. 分三种情况：
   a. 叶子节点：直接删除
   b. 单子节点：用子节点替代
   c. 双子节点：用前驱或后继替代

复杂度：O(h)
```

### 3.3 性能分析

**时间复杂度：**
| 操作 | 平均 | 最坏 |
|------|------|------|
| 查找 | O(log n) | O(n) |
| 插入 | O(log n) | O(n) |
| 删除 | O(log n) | O(n) |

**问题：**
- 性能依赖于树的平衡性
- 有序输入会导致退化

## 四、红黑树实现

### 4.1 设计动机

**解决BST的问题：**
- BST可能退化为链表
- 需要自平衡机制

**红黑树的方案：**
- 近似平衡
- 综合性能好
- 工程应用广泛

### 4.2 红黑树特性

**平衡保证：**
- 从任意节点到叶子的最长路径不超过最短路径的2倍
- 保证高度为O(log n)

**操作复杂度：**
- 查找：O(log n)
- 插入：O(log n)
- 删除：O(log n)

**实现复杂度：**
- 需要处理多种情况
- 旋转和颜色调整

## 五、散列表实现

### 5.1 设计思路

**核心思想：**
```
通过散列函数将键映射到数组索引
Hash(Key) → Index
```

**散列函数的要求：**
1. **一致性**：相同键必须映射到相同位置
2. **高效性**：计算快速
3. **均匀性**：均匀分布，减少冲突

### 5.2 冲突解决

#### 5.2.1 拉链法（Separate Chaining）

**思路：**
```
每个位置维护一个链表
冲突的元素放入同一链表
```

**结构示意：**
```
Index 0: [Key1:Val1] → [Key2:Val2]
Index 1: null
Index 2: [Key3:Val3]
...
```

**查找过程：**
1. 计算散列值：Index = Hash(Key)
2. 在对应链表中顺序查找
3. 找到或到达链表尾部

**性能分析：**
- 平均复杂度：O(n/m)，n为元素数，m为表大小
- 最坏复杂度：O(n)（所有元素冲突）
- 负载因子α = n/m，影响性能

#### 5.2.2 线性探测法（Linear Probing）

**思路：**
```
冲突时探测下一个位置
Index = (Hash(Key) + i) % TableSize
```

**探测过程：**
```
插入Key：
1. 计算初始位置 Index = Hash(Key)
2. 如果位置被占用，探测 Index+1, Index+2, ...
3. 找到空位插入

查找Key：
1. 计算初始位置 Index = Hash(Key)
2. 从该位置开始顺序查找
3. 找到Key或遇到空位（不存在）
```

**问题：**
- **聚类（Clustering）**：连续被占用的区块
- **性能下降**：聚类导致探测链变长

**改进：**
- 动态调整表大小
- 保持负载因子在合理范围

### 5.3 性能分析

**时间复杂度：**

| 操作 | 平均情况 | 最坏情况 |
|------|---------|---------|
| 查找 | O(1) | O(n) |
| 插入 | O(1) | O(n) |
| 删除 | O(1) | O(n) |

**注意：**
- O(1)是平均情况
- 实际性能依赖散列函数质量
- 负载因子影响很大

**空间复杂度：**
- O(m)，m为表大小
- 通常 m > n（表大小大于元素数）

### 5.4 散列表 vs 树结构

| 特性 | 散列表 | 平衡树 |
|------|-------|--------|
| 查找性能 | O(1)* | O(log n) |
| 有序操作 | 不支持 | 支持 |
| 内存开销 | 较大 | 较小 |
| 实现复杂度 | 中等 | 复杂 |
| 性能稳定性 | 依赖散列函数 | 稳定 |

*散列表的平均情况

## 六、实现选择策略

### 6.1 性能对比

| 实现方式 | 查找 | 插入 | 删除 | 有序性 | 推荐场景 |
|---------|------|------|------|-------|---------|
| 链表 | O(n) | O(1) | O(n) | 无 | 小规模，频繁插入 |
| 有序数组 | O(log n) | O(n) | O(n) | 有 | 查找密集，不修改 |
| BST | O(log n)* | O(log n)* | O(log n)* | 有 | 一般场景 |
| 红黑树 | O(log n) | O(log n) | O(log n) | 有 | 需要性能保证 |
| 散列表 | O(1)* | O(1)* | O(1)* | 无 | 无序查找

*平均情况

### 6.2 选择决策树

```
需要有序操作？
├─ 是 → 平衡树（红黑树/AVL）
└─ 否 → 查找密集？
    ├─ 是 → 散列表
    └─ 否 → 简单实现（链表）
```

## 七、高级主题

### 7.1 并发符号表

**挑战：**
- 多线程同时访问
- 数据一致性
- 性能优化

**解决方案：**
- 锁机制（粗粒度、细粒度）
- 无锁数据结构
- 事务内存

### 7.2 持久化符号表

**挑战：**
- 内存到磁盘的映射
- 数据持久性
- 故障恢复

**解决方案：**
- B树/B+树
- LSM树（Log-Structured Merge）
- 哈希磁盘存储

### 7.3 分布式符号表

**挑战：**
- 数据分布
- 一致性协议
- 容错处理

**应用：**
- 分布式缓存
- 分布式数据库
- 键值存储

## 八、实际应用案例

### 8.1 Java的符号表实现

**HashMap：**
- 基于散列表
- 拉链法解决冲突
- 动态扩容

**TreeMap：**
- 基于红黑树
- 保持键有序
- 支持范围查询

### 8.2 C++的符号表实现

**std::map：**
- 基于红黑树
- 有序映射
- O(log n)操作

**std::unordered_map：**
- 基于散列表
- 无序映射
- O(1)平均操作

### 8.3 数据库索引

**B+树索引：**
- 有序符号表
- 支持范围查询
- 优化磁盘I/O

**哈希索引：**
- 无序符号表
- 等值查询快速
- 内存数据库常用
