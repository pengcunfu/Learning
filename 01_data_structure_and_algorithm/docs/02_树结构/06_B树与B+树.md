# B树与B+树

## 一、背景与动机

### 1.1 为什么需要B树？

**内存 vs 磁盘的访问速度差异：**
```
内存访问：~100 ns
磁盘访问：~10 ms = 10,000,000 ns
磁盘比内存慢100,000倍！
```

**BST/AVL/红黑树的问题：**
- 设计用于内存环境
- 树的高度导致大量磁盘I/O
- 每个节点访问可能需要一次磁盘I/O

**关键洞察：**
```
如果要减少磁盘I/O次数，必须减少树的高度！
```

### 1.2 B树的设计哲学

**核心思想：**
> 通过增加每个节点的子节点数量（多路），来降低树的高度

**直观理解：**
```
传统二叉树（高度h）：
节点数 = 2^h - 1

16路B树（高度h）：
节点数 = 16^h - 1

同样的节点数，B树的高度大大降低
```

## 二、B树的定义与性质

### 2.1 B树的形式化定义

**B树**是一种多路平衡查找树，满足以下性质：

**性质1：节点结构**
- 每个节点最多有m个子节点（m阶B树）
- 每个非叶子节点（除根外）至少有⌈m/2⌉个子节点
- 根节点至少有2个子节点（除非是叶子）

**性质2：关键字数量**
- 每个节点包含k个关键字和k+1个子节点
- ⌈m/2⌉ - 1 ≤ k ≤ m - 1

**性质3：叶子节点**
- 所有叶子节点都在同一层
- 叶子节点不包含信息（可以看作外部节点）

**性质4：有序性**
- 节点内关键字递增排列
- 子树的关键字范围不重叠

### 2.2 B树的结构示意

**一个3阶B树（m=3）：**
```
        [20|40]
       /    |    \
    [10|15] [30|35] [50|60]
```

**关键字分布：**
- 根节点：20, 40
- 左子树：所有 < 20
- 中子树：20 < x < 40
- 右子树：所有 > 40

### 2.3 B树的重要参数

**阶数（Order m）：**
- 定义了B树的"宽度"
- 影响节点的容量
- 实际中通常取100-500

**最小度数（t）：**
- t = ⌈m/2⌉
- 非根节点最少有t-1个关键字
- 根节点最少1个关键字

**树的高度：**
```
含有n个关键字的m阶B树，最大高度h满足：
h ≤ log_t((n+1)/2)
```

## 三、B树的操作

### 3.1 查找操作

**查找思路：**
```
1. 从根节点开始
2. 在节点内顺序/二分查找
3. 找到则返回
4. 未找到则确定子树，递归查找
```

**性能分析：**
- 时间复杂度：O(log n)
- 磁盘I/O次数：O(log_t n)
- 比BST少得多的I/O次数

**示例：**
```
查找35：
        [20|40]
       /    |    \
    [10|15] [30|35] [50|60]

步骤：
1. 在根节点查找：35 > 20, 35 < 40 → 中子树
2. 在中子节点查找：35 = 35 → 找到！
```

### 3.2 插入操作

**插入思路：**
```
1. 找到合适的叶子节点
2. 插入关键字（保持有序）
3. 如果节点未满，完成
4. 如果节点已满，分裂节点
```

**节点分裂：**
```
满节点（m-1个关键字）：
    [K1|K2|K3|K4]

插入K5后需要分裂：
    [K1|K2] → K3 ← [K4|K5]
    ↑
中间关键字上升到父节点
```

**分裂可能向上传播：**
- 父节点可能也需要分裂
- 可能一直传播到根节点
- 根分裂时树高+1

**示例：**
```
初始（3阶B树）：
    [20]
   /   \
[10]  [30]

插入5, 15：
    [20]
   /   \
[5|10|15] [30] ← 左子节点满！

插入12：
    [20]
   /   \
[5|10|12|15] [30] ← 需要分裂！

分裂后：
    [10|20]  ← 10上升到根
   /  |    \
 [5] [12|15] [30]
```

### 3.3 删除操作

**删除思路：**
```
1. 找到要删除的关键字
2. 如果在内部节点：
   a. 用前驱或后继替代
   b. 转化为删除叶子节点
3. 如果在叶子节点：
   a. 直接删除（如果节点不至下溢）
   b. 借用或合并（如果节点下溢）
```

**下溢处理：**

**情况1：左兄弟有多余关键字**
- 从左兄弟借一个关键字
- 通过父节点中转

**情况2：右兄弟有多余关键字**
- 从右兄弟借一个关键字
- 通过父节点中转

**情况3：兄弟都刚够用**
- 合并两个兄弟
- 关键字减少
- 可能导致父节点下溢

**示例：**
```
初始：
    [10|20|30]
   /  /  \   \
 [5][15][25][35]

删除35：正常
删除30：正常
删除25：
    [10|20]
   /  /  \
 [5][15][35] ← 20和30合并

继续删除可能导致更复杂的调整...
```

### 3.4 操作复杂度

| 操作 | 时间复杂度 | 磁盘I/O |
|------|-----------|---------|
| 查找 | O(log n) | O(log_t n) |
| 插入 | O(log n) | O(log_t n) |
| 删除 | O(log n) | O(log_t n) |

**关键点：**
- log_t n << log_2 n（当t很大时）
- 磁盘I/O次数大大减少

## 四、B+树的改进

### 4.1 B+树的设计动机

**B树的"问题"：**
- 内部节点也存储数据指针
- 节点容量受限
- 范围查询效率低

**B+树的改进：**
```
1. 所有数据存储在叶子节点
2. 内部节点只存索引（关键字）
3. 叶子节点形成链表
```

### 4.2 B+树的结构

**B+树的特点：**

**特点1：数据只在叶子**
```
内部节点：[K1|K2|K3]  ← 只存索引
叶子节点：[K1,Data1|K2,Data2|...] ← 存储数据
```

**特点2：叶子节点链表**
```
所有叶子节点通过指针连接：
← [叶子1] ↔ [叶子2] ↔ [叶子3] →
支持高效的范围查询
```

**特点3：内部节点容量**
- 内部节点可以有m个子节点（m个关键字）
- 相比B树的m个子节点m-1个关键字，容量更大

### 4.3 B+树 vs B树

| 特性 | B树 | B+树 |
|------|-----|------|
| 数据存储 | 内部和叶子 | 仅叶子 |
| 内部节点 | m个子节点，m-1个关键字 | m个子节点，m个关键字 |
| 叶子节点 | 无链表 | 有链表 |
| 范围查询 | 效率低 | 效率高 |
| 查找性能 | 稳定 | 可能需要到叶子 |
| 空间利用率 | 较高 | 较低 |

### 4.4 B+树的操作

**查找操作：**
```
1. 在内部节点查找索引
2. 确定子树，向下查找
3. 到达叶子节点
4. 在叶子节点中查找（或顺序查找）
```

**插入操作：**
```
1. 找到合适的叶子节点
2. 插入数据
3. 如果叶子节点满，分裂
4. 分裂可能向上传播
```

**删除操作：**
```
1. 找到叶子节点中的数据
2. 删除数据
3. 如果节点下溢，借用或合并
4. 调整可能向上传播
```

## 五、B+树的优势

### 5.1 查找性能稳定

**为什么稳定？**
- 所有查询都要到叶子节点
- 查询路径长度固定
- 性能可预测

### 5.2 范围查询高效

**B树的范围查询：**
```
查找[20, 40]：
1. 中序遍历树
2. 可能需要多次随机访问
3. 在磁盘上性能差
```

**B+树的范围查询：**
```
查找[20, 40]：
1. 找到20的位置（叶子节点）
2. 沿链表顺序访问到40
3. 顺序访问，I/O效率高
```

### 5.3 磁盘友好

**页存储优化：**
- 每个节点对应一个磁盘页
- 一次I/O读取整个节点
- 减少I/O次数

**缓存友好：**
- 内部节点常驻内存
- 只在需要时访问叶子
- 提高缓存命中率

## 六、实际应用

### 6.1 数据库索引

**为什么数据库使用B+树？**

1. **范围查询**
```sql
SELECT * FROM users WHERE age BETWEEN 20 AND 30;
-- B+树可以高效执行
```

2. **排序**
```sql
SELECT * FROM users ORDER BY age;
-- B+树天然有序
```

3. **大数据量**
- 数据库数据量大，无法全部放入内存
- B+树优化了磁盘I/O
- 几层节点就能索引海量数据

### 6.2 文件系统

**文件系统使用B+树：**
- NTFS（Windows）
- ext4（Linux）
- HFS+（macOS）

**用途：**
- 管理文件和目录
- 快速定位文件
- 支持大文件系统

### 6.3 其他应用

**键值存储：**
- LevelDB（使用LSM Tree，思想类似）
- RocksDB
- DynamoDB

**搜索引擎：**
- 倒排索引
- 文档检索

## 七、性能分析

### 7.1 I/O性能

**关键指标：**
```
磁盘页大小：通常4KB或8KB
节点大小：等于页大小
树的阶数m：取决于关键字大小

例如：
页大小 = 4KB
关键字大小 = 8字节
指针大小 = 8字节
m ≈ 4000/16 ≈ 250

高度为3的B+树：
节点数 = 250^3 = 15,625,000
I/O次数 = 3
```

### 7.2 空间利用率

**B+树的填充因子：**
- 节点通常半满到全满
- 平均空间利用率约67%
- 可以通过调整参数优化

### 7.3 并发控制

**B+树的并发问题：**
- 多个事务同时修改
- 节点分裂/合并的同步
- 死锁处理

**解决方案：**
- 乐观并发控制
- 悲观并发控制（锁）
- 多版本并发控制（MVCC）

## 八、变种与优化

### 8.1 B*树

**改进：**
- 节点至少2/3满（而不是1/2）
- 空间利用率更高
- 分裂更复杂

### 8.2 B链接树

**改进：**
- 节点间有额外的链接
- 提高并发性能
- 简化某些操作

### 8.3 其他优化

**缓冲区管理：**
- LRU缓存
- 预读取
- 写缓冲

**压缩技术：**
- 前缀压缩
- 差值编码

## 九、总结

### 9.1 核心要点

1. **设计动机**
   - 减少磁盘I/O
   - 降低树的高度
   - 优化外部存储性能

2. **B树特点**
   - 多路平衡查找树
   - 节点可以存储多个关键字
   - 自平衡，保持平衡

3. **B+树优势**
   - 数据存储在叶子
   - 范围查询高效
   - 性能稳定

### 9.2 学习重点

1. **理解设计权衡**
   - 空间 vs 时间
   - 内存 vs 磁盘
   - 查询 vs 更新

2. **掌握核心操作**
   - 查找、插入、删除
   - 节点分裂和合并
   - 下溢和上溢处理

3. **理解应用场景**
   - 数据库索引
   - 文件系统
   - 键值存储

**B树/B+树是外部存储的基石，理解它对于理解数据库和文件系统至关重要。**
